    CachyOS + Noctalia: configuración¶

    1. Pantalla de inicio de sesión (greetd + Noctalia Greeter)¶

    El login ya no usa SDDM, sino greetd con noctalia-greeter (ver /etc/greetd/config.toml, command = "/usr/bin/noctalia-greeter-session").

    1.1 Tema y fondo de pantalla¶

    Noctalia Greeter sincroniza automáticamente el fondo de pantalla y la paleta de colores desde Noctalia Shell. Esto se controla en ~/.config/noctalia/config.toml:

    [shell.greeter_sync]
auto_sync = true

    Con auto_sync = true, no hay que configurar nada aparte en el greeter: el fondo de pantalla que se defina desde Noctalia Shell (guardado en ~/.local/state/noctalia/settings.toml, sección [wallpaper]) se aplica también en la pantalla de login.

    greeter_sync solo sincroniza fondo de pantalla y paleta de colores. No sincroniza el avatar: ese se maneja aparte (ver 1.2).

    1.2 Imagen de perfil de usuario (avatar)¶

    Hay dos avatares independientes que mantener sincronizados, cada uno con su propia fuente:

    Noctalia Shell (el que se ve dentro de la sesión, panel, bloqueo, etc.) lee la ruta definida en ~/.config/noctalia/config.toml:

    [shell]
avatar_path = "~/Pictures/Fotos Perfil/avatar.jpg"

    Noctalia Greeter (la pantalla de login) no lee esta ruta: obtiene la foto vía D-Bus de AccountsService, propiedad IconFile, que ya está configurada para apuntar a /var/lib/AccountsService/icons/jdl. Como ese directorio es de root y mi usuario no pertenece al grupo root, hace falta sudo para sobrescribir el archivo (no hace falta tocar IconFile, solo reemplazar el contenido):

    sudo cp ~/"Pictures/Fotos Perfil/avatar.jpg" /var/lib/AccountsService/icons/jdl
sudo chown root:root /var/lib/AccountsService/icons/jdl
sudo chmod 644 /var/lib/AccountsService/icons/jdl

    Es decir, para cambiar la foto de perfil en todas partes hay que:

    1. reemplazar /home/jdl/Pictures/Fotos Perfil/avatar.jpg (actualiza Noctalia Shell)
    2. correr el bloque de arriba (actualiza el Greeter).

    Si el avatar no aparece en el greeter aunque el archivo esté bien: la propiedad IconFile de AccountsService puede no estar apuntando a /var/lib/AccountsService/icons/jdl (p.ej. puede haber quedado en el valor por defecto ~/.face, que además no es legible por el greeter porque /home/jdl tiene permisos 700). Verificar y corregir:

    # ver a qué archivo apunta IconFile actualmente
busctl --system get-property org.freedesktop.Accounts /org/freedesktop/Accounts/User$(id -u) \
  org.freedesktop.Accounts.User IconFile

# si no apunta a /var/lib/AccountsService/icons/jdl, corregirlo (no requiere sudo)
busctl --system call org.freedesktop.Accounts /org/freedesktop/Accounts/User$(id -u) \
  org.freedesktop.Accounts.User SetIconFile s /var/lib/AccountsService/icons/jdl

    Este cambio lo guarda accounts-daemon de forma persistente, así que no debería hacer falta repetirlo salvo que algo vuelva a resetear la propiedad.

    1.3 Si los cambios no se reflejan en el login¶

    El auto_sync de 1.1 no siempre se dispara al instante. Si el fondo, la paleta o el avatar no aparecen actualizados en la pantalla de login:

    # Forzar que el greeter vuelva a aplicar la apariencia actual
noctalia-greeter-apply-appearance

# o, si eso no basta, reiniciar el greeter (cierra la sesión de login, no la de usuario)
sudo systemctl restart greetd.service

    1.4 Mostrar el greeter en un solo monitor¶

    Por defecto el greeter (el compositor propio de noctalia-greeter) dibuja en todas las pantallas conectadas. Esto importa sobre todo en equipos con varios monitores (por ejemplo un desktop con dos monitores y una TV): hay que decidir en cuál de todos se quiere que aparezca el login y fijarlo ("pin") explícitamente, porque el greeter no sabe cuál es "el principal" de la sesión normal.

    Paso 1 — identificar el nombre de conector de cada pantalla en ese equipo específico (estos nombres los asigna el kernel/DRM y varían de un equipo a otro, incluso con el mismo tipo de cable — en un desktop con dos monitores y una TV podrían ser, por ejemplo, DP-1, DP-2 y HDMI-A-1):

    xrandr --listmonitors

    (ver también docs/linux/comandos.md).

    Paso 2 — fijar en greeter.toml el nombre de conector elegido para ese equipo (acá NOMBRE-DEL-CONECTOR es el valor que dio xrandr en el paso 1, no un placeholder literal):

    sudo mkdir -p /var/lib/noctalia-greeter
sudoedit /var/lib/noctalia-greeter/greeter.toml

    Agregar (o completar si ya existe una sección [output]):

    [output]
name = "NOMBRE-DEL-CONECTOR"

    Luego reiniciar el greeter para que tome el cambio (ver 1.3):

    sudo systemctl restart greetd.service

    Si ese conector no está conectado en el próximo arranque, el log del greeter avisa output 'NOMBRE-DEL-CONECTOR' not connected; using all outputs y vuelve a mostrarse en todas las pantallas (no se queda con pantalla negra).

    En el Acer Aspire 7 (un solo monitor externo conectado por HDMI) el valor configurado es HDMI-A-1 (el panel interno del laptop es eDP-1).

    1.5 zsh prompt¶

    Configuración en /usr/share/oh-my-zsh/zshrc.

    2. Paquetes de R¶

    Con frecuencia hay problemas al instalar paquetes como xml2. Esto funciona:

    Sys.unsetenv(c("INCLUDE_DIR", "LIB_DIR", "PKG_CFLAGS", "PKG_LIBS"))
install.packages("xml2")

    3. Transparencia y apariencia de ventanas (Hyprland)¶

    Esto no se configura en Noctalia. Noctalia Shell (~/.config/noctalia/config.toml) solo controla la apariencia de la barra, el panel y los widgets; la transparencia, los bordes y el desenfoque de las ventanas los controla Hyprland directamente, en ~/.config/hypr/config/decorations.lua:

    hl.config({
    general = {
        gaps_in = 3,
        gaps_out = 8,
        border_size = 2,
        col = {
            active_border = { colors = { CACHYLGREEN, CACHYDGREEN }, angle = 45 },
            inactive_border = CACHYGRAY,
        },
    },
    decoration = {
        rounding = 10,
        active_opacity = 0.95,
        inactive_opacity = 0.65,
        fullscreen_opacity = 1,
        blur = {
            size = 5,
            passes = 4,
            special = true,
        },
    },
})
    • decoration.active_opacity: opacidad de la ventana con foco (1 = opaca, 0 = invisible).
    • decoration.inactive_opacity: opacidad de las ventanas sin foco (la que normalmente se quiere bajar para distinguir cuál está activa).
    • decoration.fullscreen_opacity: opacidad en modo pantalla completa.
    • decoration.rounding: redondeo de esquinas.
    • decoration.blur: desenfoque del fondo detrás de ventanas transparentes (size, passes).
    • general.border_size, general.gaps_in, general.gaps_out: tamaño de borde y espacios entre ventanas.
    • general.col.active_border / inactive_border: color del borde según foco.

    Después de editar y guardar el archivo, los cambios se aplican solos (Hyprland recarga la configuración Lua automáticamente). Si no se reflejan, forzar con:

    hyprctl reload

    3.1 Por qué la transparencia se ve distinta según la aplicación¶

    active_opacity / inactive_opacity no se ven igual en todas las aplicaciones porque dependen de si la ventana expone un canal alfa real al compositor:

    • Aplicaciones con alfa real (VSCodium, terminales como kitty): Hyprland puede mezclar de verdad el fondo detrás de la ventana, así que se ve la transparencia y el desenfoque (blur) tal como se configuraron.
    • Aplicaciones sin alfa real (p. ej. Tauon Music Box, que usa un renderizador propio en vez de GTK, o GNOME Text Editor en GTK4/libadwaita): al no exponer un canal alfa, Hyprland no tiene nada que mezclar detrás y solo puede simular la opacidad oscureciendo/aclarando los píxeles ya renderizados de toda la ventana (texto e iconos por igual). Se ve "lavado" al perder el foco, y sin ningún desenfoque real.
    • Zen Browser (y Firefox): no es una limitación técnica sino una regla explícita en windowrules.lua que fuerza opacidad 1.0 para esas clases, porque los navegadores basados en Gecko suelen tener artefactos visuales con transparencia real.

    Para evitar el efecto "lavado" en aplicaciones sin alfa real, se les fuerza opacidad 1.0 igual que a Zen/Firefox o a los reproductores de video, en ~/.config/hypr/config/windowrules.lua:

    hl.window_rule({ match = { class = "^(tauonmb|org\\.gnome\\.TextEditor)$" }, opacity = "1.0 override" })

    Para agregar otra aplicación a esta lista, hay que conocer su class de ventana. Se obtiene con la sesión de Hyprland activa:

    hyprctl clients | grep -B2 "class:"

    4. Fuentes¶

    Las fuentes de usuario se guardan en /usr/local/share/fonts (requiere sudo).

    Para copiar varias carpetas de fuentes desde ~/Downloads/ de una sola vez:

    sudo cp -r ~/Downloads/{fuente_1,fuente_2,fuente_3} /usr/local/share/fonts/
sudo fc-cache -f -v
    • -r copia carpetas recursivamente
    • Las llaves {} expanden múltiples nombres en un solo comando
    • fc-cache obliga al sistema a reconocer las nuevas fuentes

    5. Botones de ventana en apps GTK4/libadwaita¶

    Síntoma: GNOME Text Editor (y cualquier app GTK4/libadwaita) a veces mostraba los botones de minimizar, maximizar y cerrar, y a veces no.

    Causa: depende del estado de la ventana en Hyprland. En mosaico, libadwaita oculta el widget windowcontrols; en flotante, lo dibuja. El ajuste org.gnome.desktop.wm.preferences button-layout (aquí 'appmenu:close') no influye en esto.

    Solución: al final de ~/.config/gtk-4.0/gtk.css, después de @import url("noctalia.css");, hay una regla que oculta siempre esos controles:

    /* Oculta siempre los controles de ventana CSD (min/max/cerrar),
   sin importar el estado flotante/mosaico en Hyprland. */
windowcontrols,
windowcontrols > button {
  opacity: 0;
  min-width: 0;
  min-height: 0;
  margin: 0;
  padding: 0;
  border: none;
  background: none;
  box-shadow: none;
}
    • Noctalia regenera noctalia.css al cambiar de tema, pero no toca gtk.css, así que la regla se mantiene. Si los botones vuelven a aparecer (por ejemplo, tras reinstalar un tema GTK), verificar con grep windowcontrols ~/.config/gtk-4.0/gtk.css que la regla siga al final.
    • No hace falta reiniciar: GTK4 lee gtk.css al crear cada ventana nueva.
    • Afecta a todas las apps GTK4. Para ocultarlos solo en una app, acotar el selector (por ejemplo, window.org-gnome-TextEditor windowcontrols).
    • En la época de HyDE, la regla también debía ir en la plantilla de wallbash (~/.local/share/wallbash/theme/gtk/gtk4.dcol), porque wallbash regeneraba gtk.css. Con Noctalia ya no es necesario.

    6. Inactividad: bloqueo, apagado de pantalla y suspensión¶

    Configurado en Noctalia, en Settings → Power → Idle (se guarda en la sección [idle] de ~/.local/state/noctalia/settings.toml):

    Acción Tiempo
    lock (bloquear) 60 s
    screen-off (apagar pantalla) 70 s
    suspend (suspender) 600 s
    • El bloqueo siempre va antes que el apagado de pantalla. Si screen-off ocurre primero, hyprlock enciende el monitor para mostrar la contraseña y nada lo vuelve a apagar.
    • Desvanecido previo: antes de cada acción, Noctalia muestra una capa negra con desvanecido (pre_action_fade_seconds, 2 s por defecto). Parecía que el monitor se apagaba a los 60 s y se volvía a encender al bloquear, pero era solo esa capa. Se desactivó con pre_action_fade_seconds = 0 (control "Pre-action fade" en la misma pantalla).
    • Suspensión sin bloqueo previo: la acción suspend tiene lock_before_suspend = false. Es seguro porque a los 600 s la sesión ya lleva 9 minutos bloqueada. Si algún día el bloqueo se sube a un tiempo cercano o mayor que la suspensión, activar esa opción.

    Para revisar qué acciones registró Noctalia y en qué orden:

    grep -i "idle" ~/.cache/noctalia/noctalia.log | tail -30

    7. Restos de HyDE: HYPRLAND_CONFIG apuntaba a la configuración vieja¶

    Síntoma (tras migrar de HyDE a Noctalia): HYPRLAND_CONFIG seguía apuntando a ~/.local/share/hypr/hyprland.conf (la configuración de HyDE) en vez de ~/.config/hypr/hyprland.lua, incluso después de reiniciar.

    Causa: HyDE dejó el archivo ~/.config/uwsm/env-hyprland.d/00-hyde.sh con una asignación directa de HYPRLAND_CONFIG. uwsm carga ese archivo después de ~/.config/uwsm/env-hyprland (que tiene el valor correcto), así que el de HyDE siempre ganaba.

    Solución: en 00-hyde.sh se borró la línea HYPRLAND_CONFIG=... y se quitó HYPRLAND_CONFIG de la lista del export. El valor correcto queda definido solo en ~/.config/uwsm/env-hyprland:

    export HYPRLAND_CONFIG=/home/jdl/.config/hypr/hyprland.lua

    Verificación (tras cerrar sesión y volver a entrar):

    systemctl --user show-environment | grep HYPRLAND_CONFIG

    Si alguna variable de entorno de la sesión no toma el valor esperado, revisar primero ~/.config/uwsm/env-hyprland.d/, porque ahí pueden quedar más restos de HyDE.
